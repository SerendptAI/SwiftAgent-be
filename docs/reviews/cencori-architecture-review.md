# Architecture Review: Cencori AI Gateway Proposal vs SwiftAgent-be

**Date:** July 15, 2026
**Reviewer:** Chukwuebuka-2003

---

## 1. Current Model Request Flow

```
FastAPI Chat Endpoint
  → LangGraph Orchestrator (fast_routing model)
    → Specialist Agent (knowledge / navigation / api / scraper)
      → Direct SDK call via LangChain adapters:
          ChatAnthropic / ChatGoogleGenerativeAI / ChatOpenAI
```

All provider SDK calls happen **directly** through LangChain wrappers in `app/services/graph/llm_factory.py`. There is no intermediary gateway, proxy, or control layer between the application and the AI providers.

## 2. Architecture Deep-Dive

### 2.1 Provider Configuration

Three providers are configured via environment variables (`app/core/config.py`):

| Provider | Env Key | Default Model |
|---|---|---|
| Anthropic | `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` | `claude-haiku-4-5-20251001` |
| Google Gemini | `GEMINI_API_KEY` / `GEMINI_MODEL` | `gemini-2.5-flash` |
| OpenRouter | `OPENROUTER_API_KEY` / `OPENROUTER_MODEL` | `google/gemma-4-31b-it:free` |

Each is instantiated in `llm_factory.py` with a fallback cascade — if the requested provider's key is missing, it falls through to Anthropic → Gemini.

### 2.2 LangGraph Multi-Agent Orchestration

The system uses **LangGraph** with a `StateGraph`:

```
START → Orchestrator ─┬→ Knowledge Agent ───→ Knowledge Tools (RAG)
                      ├→ Navigation Agent ──→ Navigation Tools (stroll)
                      ├→ API Agent ─────────→ API Tools (integrations)
                      ├→ Scraper Agent ─────→ Scraper Tools (page reader)
                      └→ Human Handoff ─────→ Email ticket creation
```

- **Orchestrator** (`orchestrator.py`): Uses `fast_routing=True` (smaller/faster model) to classify intent via tool calling. Routes to one of 4 specialist agents or handles the chat directly for simple greetings.
- **Each agent node** gets its own LLM instance (full-size model) bound to domain-specific tools.
- **Streaming**: Token-by-token streaming via `astream_events()` with SSE delivery to clients.

### 2.3 Provider Failover (Existing)

In `chat.py` (the SSE generator), there's a **sequential retry loop**:

```python
agents_to_try = [agent_key, "openrouter", "gemini"]
for provider_key in agents_to_try:
    try:
        async for event in chat_stream_graph(..., agent_provider=provider_key):
            ...
        break  # Success — exit loop
    except Exception:
        continue  # Try next provider
```

This is coarse: the entire conversation is retried against the fallback provider. No per-request failover, no degradation detection, no latency-aware routing.

### 2.4 Observability (Existing — Langfuse)

Already has a mature observability layer in `app/core/langfuse.py`:

- `@observe()` decorator on every agent node and orchestrator
- `create_llm_generation()` for detailed per-call spans
- Captures: input/output tokens, model name, provider, latency, `company_id`, `session_id`, `user_id`
- Streaming traces capture final output
- Tool calls recorded as child spans

**Missing from current observability:**
- Cost estimation ($/request based on model pricing)
- Per-workspace or per-customer cost breakdown
- Usage trends dashboards

### 2.5 Usage Governance (Existing — Basic)

- `app/core/plan_enforcement.py`: Limits based on chat count and stroll count per billing tier
- `app/core/rate_limiter.py`: Per-endpoint rate limiting (chat, auth)
- `app/core/billing_limits.py`: Plan-based feature gates

**No token-level budgets, no per-workspace model restrictions, no cost thresholds.**

### 2.6 Context Management

- `MAX_CONTEXT_MESSAGES=10` in config
- Memory system: session-scoped working memory + episodic summaries (generated by Gemini)
- Working memory has a 1-hour TTL
- No prompt compression, no context budget management, no smart truncation

## 3. Cencori Proposal: Gap Analysis

| Cencori Proposal | SwiftAgent Current State | Gap | Priority |
|---|---|---|---|
| **Centralized AI Gateway** | Direct SDK calls per provider | ✅ Real gap — a proxy layer would consolidate auth, config, routing, and logging | Medium |
| **Model Routing by Complexity** | Only domain-based routing (orchestrator by intent). Same model for all workloads within a domain | ✅ Real gap — FAQ vs complex troubleshooting use same model chain | **High** |
| **Token/Cost Observability** | Langfuse already captures tokens, latency, model, provider. Missing: cost estimation, per-customer breakdown | ⚠️ Partial — core infra exists, needs cost layer on top | Low |
| **Usage & Budget Controls** | Plan-level chat/stroll count limits only. No token budgets or per-workspace model restrictions | ✅ Real gap — no granular cost governance | **High** |
| **Provider Failover** | Coarse sequential retry (conversation-level, not per-request) | ⚠️ Partial — basic failover exists but lacks degradation detection | Medium |
| **Context Optimization** | Fixed `MAX_CONTEXT_MESSAGES=10`, no smart truncation or compression | ✅ Real gap — no context budget management | Medium |
| **Cost Attribution** | No cost per agent, customer, or workspace | ✅ Real gap — Langfuse has the data but no cost layer | **High** |

## 4. Key Architectural Insights

### 4.1 The Cencori Integration Point

The natural insertion point is `app/services/graph/llm_factory.py`. Every model request flows through `get_llm()`. Wrapping calls through a Cencori gateway URL (instead of direct SDK endpoints) would give them visibility over **all** traffic without changes to the graph structure.

Current code path:
```
get_llm() → ChatAnthropic(api_key=..., model=...)
```

With Cencori:
```
get_llm() → ChatOpenAI(base_url="https://cencori-gateway/...", api_key=cencori_key, model=mapped_model)
```

### 4.2 The Orchestrator Already Routes

The orchestrator in `orchestrator.py` already routes by intent — but it routes to *domain experts*, not by *complexity tier*. Adding a `complexity` classifier to the orchestrator that selects model per-turn (cheap model for FAQs, capable model for troubleshooting) could be done without Cencori.

### 4.3 Langfuse Reduces Cencori's Observability Value

Since Langfuse already captures:
- Per-call token counts
- Per-provider/model spans
- Latency
- Session/user/company metadata

The incremental value Cencori adds in observability is limited to **cost estimation** (Langfuse doesn't track $/token) and **cost dashboards**. This could also be done with a small cost calculation layer on top of Langfuse data.

### 4.4 Where Cencori Adds Genuine Value

1. **Cost-based model routing per turn** — the single biggest lever
2. **Token budget enforcement per customer/workspace** — currently impossible
3. **Smart failover** — with degradation detection, not just try-another-provider
4. **Cost attribution** — per-agent, per-customer, per-workspace

## 5. Recommended Next Steps for Swift Agents

### If exploring integration:

1. **Insert Cencori as a proxy in `llm_factory.py`** — route all provider calls through Cencori's gateway URL
2. **Keep Langfuse active** — dual observability during pilot for comparison
3. **Pilot scope**: One agent domain (e.g., Knowledge Agent) with cost-based model routing
4. **Key metric**: Cost per successful customer resolution, not just cost per token

### If building in-house alternatives:

1. **Cost layer on Langfuse** — `cost = tokens × model_pricing_table` is trivial
2. **Per-workspace token budgets** — add `tokens_budget` to company/billing plans
3. **Complexity classifier in orchestrator** — classify turns as "simple" / "complex" and route to different model tiers
